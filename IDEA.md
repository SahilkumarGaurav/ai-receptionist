# AI Dental Receptionist — Private Doctor Dashboard MVP

Build a **private, modern doctor dashboard** for my existing AI Dental Receptionist project.

## IMPORTANT

This dashboard must integrate with my **existing Python `main.py` backend**.

**Do NOT rewrite, replace, or break my existing AI receptionist logic.**

Do NOT add Google Calendar integration yet.

Do NOT add payments, WhatsApp, SMS, analytics, subscriptions, medical records, or other advanced features.

The goal is only to create a working MVP where the dentist can see appointment bookings generated by the AI receptionist.

---

## 1. Private Doctor Login

Create a simple private login page.

Route:

`/login`

After successful login:

`/dashboard`

The dashboard must not be publicly accessible without authentication.

For the MVP, use a simple authentication system that can later be replaced with Firebase/Supabase authentication.

---

## 2. Dashboard Layout

Create a clean, professional dental-clinic dashboard.

Use a modern medical SaaS style.

### Sidebar

Include:

* Dashboard
* Appointments
* Patients
* Settings
* Logout

For the MVP, only Dashboard and Appointments need to be fully functional.

---

## 3. Dashboard Overview

The main dashboard should show:

### Today's Appointments

Display the number of appointments scheduled for today.

### Pending Appointments

Display the number of appointments waiting for doctor confirmation.

### Confirmed Appointments

Display the number of confirmed appointments.

### Upcoming Appointments

Show a list/table of upcoming bookings.

Each booking should display:

* Patient name
* Appointment date
* Appointment time
* Type of dental service
* Status

Example:

| Patient      | Date        | Time    | Service         | Status    |
| ------------ | ----------- | ------- | --------------- | --------- |
| Rahul Sharma | 18 Aug 2026 | 4:00 PM | Dental Cleaning | Pending   |
| Priya Singh  | 18 Aug 2026 | 5:00 PM | Consultation    | Confirmed |

---

## 4. Appointments Page

Create:

`/appointments`

This should be the main appointment-management page.

Display all appointments in a clean table.

Required fields:

* Appointment ID
* Patient Name
* Date
* Time
* Dental Service
* Status

Possible statuses:

* Pending
* Confirmed
* Rejected
* Cancelled
* Completed

Use visually distinct status badges.

---

## 5. Appointment Actions

For pending appointments, the doctor should have:

### Confirm

Button:

`Confirm`

When clicked:

* Change appointment status from `pending` to `confirmed`
* Send the update to the Python backend
* Update the dashboard immediately

### Reject

Button:

`Reject`

When clicked:

* Change status to `rejected`
* Update the Python backend
* Update the dashboard

For confirmed appointments:

* Cancel
* Mark as Completed

Do not implement complex rescheduling yet.

---

## 6. Patient Information

For the MVP, store/display only basic patient information:

* Patient name
* Phone number
* Email if available
* Appointment date
* Appointment time
* Requested dental service

Do NOT build detailed medical records yet.

## 7. AI Receptionist → Backend → Dashboard Connection

The most important requirement is that appointments created by the AI receptionist must appear automatically in the doctor dashboard.

The architecture should be:

Patient
→ AI Receptionist
→ `main.py`
→ Appointment API
→ Dashboard

The dashboard must NOT use hardcoded fake appointment data in the final implementation.

---

## 8. Python Backend API

Modify the existing `main.py` only where necessary.

Create API endpoints similar to:

### Get appointments

`GET /api/appointments`

Returns appointment data.

Example response:

```json
[
  {
    "id": "001",
    "patient_name": "Rahul Sharma",
    "date": "2026-08-18",
    "time": "16:00",
    "service": "Dental Cleaning",
    "phone": "XXXXXXXXXX",
    "status": "pending"
  }
]
```

### Create appointment

`POST /api/appointments`

Used by the AI receptionist when a patient books an appointment.

### Confirm appointment

`PATCH /api/appointments/{id}/confirm`

Changes status to:

`confirmed`

### Reject appointment

`PATCH /api/appointments/{id}/reject`

Changes status to:

`rejected`

### Cancel appointment

`PATCH /api/appointments/{id}/cancel`

Changes status to:

`cancelled`

### Complete appointment

`PATCH /api/appointments/{id}/complete`

Changes status to:

`completed`

Use the existing backend architecture wherever possible instead of unnecessarily creating duplicate systems.

# Final MVP Workflow

The final working flow must be:

Patient calls AI receptionist
→ AI collects patient information
→ AI receives appointment request
→ `main.py` creates appointment
→ Appointment is stored
→ Doctor opens private dashboard
→ New appointment appears
→ Doctor clicks Confirm
→ `main.py` updates appointment status
→ Dashboard shows Confirmed

This workflow is the primary success criterion for the MVP.

## Development Rule

Before modifying existing files:

1. Inspect the existing project structure.
2. Understand how `main.py` currently handles the AI receptionist.
3. Identify the existing appointment/booking logic.
4. Reuse existing functions wherever possible.
5. Do not duplicate existing functionality.
6. Do not delete working code.
7. Do not introduce Google Calendar yet.
8. Clearly separate frontend and backend responsibilities.
9. Keep the implementation simple enough to extend later.

The final result should be a **working private dentist dashboard connected to the existing AI receptionist backend**, not just a static UI mockup.
